# Кандидатогенерация для поиска услуг Авито

**Итог: Recall@50 = 0.84 на бенчмарке** (`answer.csv`).

Задача: по поисковому запросу (текст, город, фильтры) отобрать из корпуса в 189 212 объявлений до 50 кандидатов так, чтобы среди них оказалось объявление, которое пользователь в итоге выбрал. Метрика — Recall@50 (среднее по запросам доли найденных ответов, порядок внутри топ-50 не важен).

Мой принцип: recall не смотрит на порядок, только на попадание. Поэтому я строю один сильный пул (радиус + текст) и аккуратно переупорядочиваю его, а не отрезаю жёсткими фильтрами.

## 2. Анализ данных

Полный разбор — `notebooks/01_eda.ipynb` (прогон с outputs внутри).

Пять фактов, на которых построено решение:

1. **Корпус train почти не покрывает.** Только 18 142 объявлений корпуса (9.6%) хоть раз выбирали в train. Запоминание «запрос → ответ» бесполезно — нужен обобщающий поиск.
2. **Город решает почти всё.** 83.1% ответов — из того же города, что и поиск. Но резать строго по городу нельзя: 17% ответов чужие, есть соседи и дальний выбор.
3. **Категория почти не разделяет.** В бенчмарке всего два значения категории поиска (2230 против 222), в парах train совпадение с категорией объявления 0.9999. На неё не опираюсь.
4. **Дальше 30 км выбирают редко.** 4.3% дальше 30 км, 2.2% дальше 100 км. Радиус с запасом покрывает почти всё, но дальний хвост существует.
5. **Фильтры написаны теми же словами, что параметры.** У 36.9% запросов фильтры есть («Вид услуги Красота» дословно входит в параметры). Их стоит считать отдельно, а не мешать в запрос.
6. **Запросы короткие, описания длинные.** Медиана запроса 22 буквы, заголовка 35, описания 1054. Документ собираю из заголовка и начала описания, хвост выкидываю.

## 3. Подход

```text
запрос ──┬─ BM25 по леммам (заголовокx3 + параметры + описание[:600])
         ├─ bi-encoder e5-small, доученный на кликах (косинус)
         └─ фильтры отдельным бонусом + чистка раскладки
                │
пул = всё в радиусе 50 км от центра города (иначе свой город)
                │
порядок = BM25/max + 0.3 x близость + 0.55 x бонус + 0.5 x косинус/max
                │
топ-50 (+ добивка глобальным топом, если пул меньше 50)
```

Каждый элемент закрывает факт из анализа:

| Элемент | Почему |
|---|---|
| BM25 по леммам, заголовок x3 | запросы короткие и терминологичные, точное совпадение — сильный сигнал; лемматизация pymorphy3 закрывает окончания |
| Описание только первые 600 букв | начало несёт суть услуги, хвост («время для связи») шумит; полное описание давало столько же, но дольше |
| Радиус 50 км + вес близости | факт 2 и 4: соседи находятся, дальние не режутся; близость внутри пула упорядочивает лучше жёсткого города |
| Фильтры отдельным бонусом | факт 5: совпадение фильтра с параметрами точнее считать отдельно (бонус 0.55 за покрытие >= 90%) |
| Чистка раскладки | часть запросов набрана в чужой раскладке («ktrnhbrf»), BM25 их не видит вообще |
| Bi-encoder e5-small | синонимы и перефразировки, где лексика слепая; сам по себе слаб (0.294), как добавка +0.015 |

Что не вошло и почему — в таблице гипотез ниже.

## 4. Валидация

Отправок всего 7, поэтому качество я мерил сам, на честных сплитах:

- **Быстрые проверки:** 200 пар из train, чьи ответы лежат в корпусе (seed 42). Меняю один пункт за раз.
- **Стабильные проверки:** 500 пар (seed 123). Клики для формул считаю без проверяемых групп целиком — как на бенчмарке, где кликов по запросу нет.
- **Финал:** 2000 свежих групп запросов, macro-recall (seed 99).
- **Профиль бенчмарка:** тексты, выкинутые из статистики целиком (seed 456), и сегмент «нулевая цель + новый текст».

Главный урок валидации: плюс на грязных кликах (свои клики не выкинуты) — это утечка, а не сигнал. Все сетки с кликами я перепроверял на чистых данных, и дважды это меняло вердикт (разделы 5 и 8 таблицы).

| Отправка | Что это | Бенчмарк |
|---|---|---|
| 1 | текст + 0.3 x близость (r=30) + 0.1 x популярность | 0.775839 |
| 2 | то же без популярности (вредит нулевым целям: -0.022) | 0.780682 |
| **3 (итог)** | **+ фильтр-бонус + раскладка + радиус 50 + 0.5 x dense** | **0.84** |

## 6. Анализ ошибок и что я сделал

- **Некликаные цели.** Цели бенчмарка на ~90% некликаные, а популярность давила их вниз (-0.022). Убрал популярность из ответа: 0.7758 → 0.7807 на платформе.
- **Утечки через свои клики.** Поймал дважды: преимущество «нового чемпиона» и части плюса популярности исчезали на чистых данных. Правило: сетки только на данных без проверяемых групп.
- **Трудный сегмент.** Нулевые цели + новые тексты дают 0.77 против 0.89 в среднем — это и есть профиль бенчмарка. Против него работают широкое geo и dense, а не популярность.
- **Пул vs топ.** Пул радиуса находит почти всё (0.955+), потери — внутри топ-50. Дальше расти можно ранкером поверх пула (не успел).

## 7. Как воспроизвести

```bash
python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
# data/*.parquet с Яндекс-диска, models/* с Google Drive (раздел 1)
python -m src.pipeline       # → answer.csv
python check_answer.py       # проверка формата
```

- Все сиды зафиксированы: сплиты 42/123/99/7/456; пары для обучения bi-encoder 200000 (seed 42), val 2000 (seed 42).
- Дообучение bi-encoder на GPU недетерминировано до бита, поэтому побитово тот же `answer.csv` получается только с приложенными весами. Модель: `intfloat/multilingual-e5-small`, 1 эпоха MNR-лоссом, батч 32, max_seq_length 128.
- Внешних API нет: веса и данные скачиваются один раз, дальше всё локально.
